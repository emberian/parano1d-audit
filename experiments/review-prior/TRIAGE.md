# C1–C27 re-triage: attacker powers, observed outcomes, missing links

2026-11-15, pinned commit `52938433a30b185ab007afaa15166a632cf2e82e`.
This is an **operational** ranking: what an adversary has made happen to a
deployed-path node or user in the saved local work. It does not rank the
importance of correcting a false paper theorem or a broken primitive. Read
alongside [REPORT.md](REPORT.md), [TAKEOVER.md](../TAKEOVER.md), and the
new evidence linked below. No public network was attacked.

## Best deployment-facing leads beyond C1–C27

1. **W7 receive-address substitution:** a local RPC impostor can supply an
   attacker address as the GUI backend's active receive address; an independent
   pinned wallet builder signed a synthetic payment to it
   (`wallet-boundary/README.md`). The Copy Address UI and a mined recipient
   outcome were source-traced, not executed. This is the clearest conditional
   direct-diversion path: no stolen victim key is necessary, but local RPC or
   software-distribution control is.
2. **Wallet send acknowledgment:** an isolated sender returned success and a
   txid while an independent receiver had no mempool entry; after connection
   the receiver learned the same txid (`operator-exit/REPORT.md`). This can
   mislead a user about deposit delivery, but does not establish targeted
   operator censorship or an exchange-side selling lockout.
3. **Finality off by one:** source permits replacing an 18-block suffix while
   docs imply a 17-block maximum (`chain-malice/REPORT.md`). At 18
   tip-inclusive confirmations a recipient may still be reorged; 19 cross the
   local boundary. Double-spend significance depends on an exchange or merchant
   actually crediting at 18 and an attacker producing a heavier valid fork.

For the original “operator sells while holders cannot” question, no present
result demonstrates that asymmetry. The nearest paths are local wallet
deception, unconfirmed-broadcast acknowledgment, and ordinary producer
discretion. None attributes sustained miner/network control or SafeTrade
deposit policy to the developer. A fair public report should state those
unknowns and keep native NOID, native assets, and exchange balances distinct.
