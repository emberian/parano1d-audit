# Coinbase-slot control and the wallet reservation result

Source-only review of pinned Parano1d commit `52938433a30b185ab007afaa15166a632cf2e82e`. No new block, proof, or network test was run. The existing [full-proof local fixture](../verification-wallet/README.md) chose the wallet transaction's output hint to match the next block's predicted coinbase slot. That proves a reachable local wallet/mempool desynchronization; it does not itself establish that a miner can aim it at an arbitrary submitted transaction.

## What a normal miner does

The ordinary wallet RPC chooses empty output slots with a per-call nonce and tip-state seed before proving and submitting a payment (`noid_rpc/src/server.rs:1030-1117`; `wallet_submit.rs:87-190`). Its signed transaction fixes those output slots. The miner's template then chooses its coinbase slot from parent State and a deterministic reuse seed, with the selected transaction slots reserved (`noid_chain/src/consensus/template.rs:893-915`). The template also receives output slots reserved by mempool transactions even when those transactions are not selected (`noid_miner/src/template.rs:380-434`, `noid_mempool/src/mining.rs:93,225-230`). When its preferred coinbase slot belongs to a pending transaction, it searches up to 64 nearby empty, unreserved slots first (`noid_chain/src/consensus/template.rs:500-528`). Thus a stock miner that knows and admits the victim's transaction actively avoids the observed collision in ordinary sparse State. The fallback is allowed if no alternative appears in that small search, so this is a preference, not a consensus guarantee.

## What consensus and a custom producer allow in source

`validate_mandatory_coinbase` checks coinbase framing, parent anchor, payout owner, and emission schedule, but does not require the miner's template allocator to pick a particular slot (`noid_chain/src/consensus/validation.rs:310-370`). The state transition checks that each live output slot is in range, unused within the block, and empty in the parent state (`noid_chain/src/state_delta.rs:250-280`). This source path suggests a producer able to author and prove a nonstandard block has latitude to place its coinbase into an empty slot fixed by a pending ordinary payment, provided it excludes that payment from the block and satisfies all remaining block/proof rules. We did **not** execute such a targeted custom-producer block; the full-proof fixture arranged the collision from the wallet side. Winning or otherwise supplying an accepted block is still required. This ability is a block-producer choice, not a privileged operator command.

## What the resulting wallet effect is

After a different accepted block occupies the pending payment's output slot, the mempool emits `TxEvicted(OutputSlotOccupied)` (`noid_mempool/src/pool.rs:816-846`). The node's mempool event relay handles `TxAdmitted` for gossip and ignores other events (`noid_node/src/main.rs:2355-2377`); the ordinary wallet scanner clears reserved input slots when a block actually *spends* those inputs, not when an unrelated coinbase occupies the payment's proposed output (`noid_node/src/wallet/scanner.rs:286-294,395-400`). Its block update removes the pending *output* reservation for that slot (`noid_node/src/wallet/mod.rs:183-196`). Consequently the original input can remain a live on-chain UTXO yet show as reserved/unspendable in that local wallet, as the full-proof fixture observed. Reloading the wallet clears the in-memory reservation; the pending history row remains (see [full-run.log](../verification-wallet/full-run.log)). The chain does not freeze the UTXO or transfer it away.

This exact collision route has been demonstrated for an **ordinary payment**. Trade intents instead commit funding inputs and policy, and their mempool admission checks those live inputs (`noid_mempool/src/trade.rs:132-155`); they do not carry a fixed ordinary-payment output slot for the coinbase to occupy. The native pending-wallet hook also retires records when accepted block inputs or outputs overlap them (`noid_node/src/wallet/native.rs:242-265`). We have no demonstration that this route blocks token sales, persists through a wallet restart, affects other wallets, or gives the network operator a capability unavailable to any producer of valid blocks. A miner can choose inclusion and exclusion of its own block independently of this wallet bug, but selective, sustained suppression of others' sales while selling its own remains unproved.
