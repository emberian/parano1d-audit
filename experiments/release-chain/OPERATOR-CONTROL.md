# Operator control through software and bootstrap

Target: `parano1d/` at `52938433a30b185ab007afaa15166a632cf2e82e` (the release-relevant files checked against `v2.1.0` in [REPORT.md](REPORT.md)). This is a source-only review. It neither connects to mainnet nor proves who controls the domain, development fund keys, mining work, or release accounts.

## Verdict

The current reference node has **no identified remotely activatable developer key, admin transaction, update feed, mutable consensus checkpoint, or command that lets the publisher selectively unlock its own coins while freezing another holder's coins**. Its genesis, fork schedule, network profile, proof banks, and development payout recipients are compiled or embedded. A maintainer can publish changed source and binaries, and users who install those binaries trust that new program. The installed binary does not acquire new rules merely because a new release appears.

The current unilateral *network-facing* control point is narrower: four default, identity-unpinned DNS seeds under `parano1d.org`. A DNS controller can choose a fresh node's initial endpoints, with the strongest practical effect when no independent peers are reachable. That can impair discovery or bias an initial view; it does not by itself authorize invalid state, erase a returning node's finalized chain, or give selective spending rights. Domain control by the developer is plausible but unproved by this source review. See [the separate bootstrap survey](../operator-power/REPORT.md) for dated DNS observations and [snapshot review](../snapshot-adversary/REPORT.md) for the work-ranked initial-sync boundary.

The source search for an updater or remote release downloader in `noid_gui/src` and `noid_node/src` found no such path; GUI startup selects a local binary. This is a scoped negative finding, not a proof about third-party installers or package managers. A third-party Android wallet reportedly compiles in a later header checkpoint; that is outside the reference node and belongs to its publisher, not this binary ([bootstrap survey](../operator-power/REPORT.md)).

## Distribution and new installations

The documented release procedure starts from synchronized, clean `main`, runs Platform CI, creates an annotated tag on canonical Forgejo plus GitHub and GitLab mirrors, opens a GitHub draft, and dispatches Native Release (`scripts/publish_release.sh:175-223,288-316`; `.github/RELEASING.md:1-17`). Native Release is manually dispatched and requires the tag, pack SHA-256 values, and successful Platform CI for that exact commit (`.github/workflows/release.yml:5-39,165-171`). It verifies pack archive digests and layouts before the five platform builds, then uses those approved archives (`release.yml:173-205,299-337`). Current default is `retired_history=true`; legacy matrices are omitted, with the embedded verified ancestry certificate supplying the transition (`release.yml:35-39,323-337`; `.github/RELEASING.md:35-43`). The legacy-matrix gap in standalone `build_release.sh` therefore does not directly affect default v2.1 artifacts; [C16 reassessment](REPORT.md) gives the narrower transition/custom-build boundary.

The workflow publishes `SHA256SUMS` alongside the ten binaries and three packs (`release.yml:418-456`). Users are told to compare downloads to that same-release file (`docs/getting-started/wallet.md:20-37`). This detects accidental or third-party byte substitution **when the checksum file is trusted independently of the changed download**, but a publisher or compromised release account able to change both can make them agree. The scripts show reproducible **pack normalization** and checked build inputs; this review found no independent, publicly verified bit-for-bit rebuild of the published v2.1 executables. The release scripts do not create a detached artifact signature. The macOS packaging default uses ad-hoc `codesign --sign -`, with an optional identity; the user guide says Windows Authenticode signing and Apple Developer ID notarization are not in place (`scripts/release/package_macos_gui.sh:117-128`; `docs/getting-started/wallet.md:56-67`). An annotated Git tag is a release identity in these scripts, not an independently verified signature over the binaries.

A malicious **newly installed** node or GUI could in principle reject selected transactions locally, divert wallet sends, disclose local secrets, change bootstrap names, or adopt different consensus rules. That is the ordinary software-distribution trust boundary: the victim must install/run the changed executable (or point the GUI at an attacker-controlled RPC). Existing honest nodes would not automatically accept incompatible consensus blocks; a released policy to omit certain valid transactions would need adoption by the miners/relays that matter to cause sustained censorship. The current source contains no evidence that the publisher has made such a change or has the required mining/network dominance. Same-channel hashes, release mirrors copying identical assets, and unsigned packages do not establish that it has happened.

## Claim suitable for public use

“The reference client has no demonstrated remote developer switch for freezing holders while letting a favored address spend. Its default clean-install bootstrap does trust four unpinned DNS names under one domain, and official binary downloads depend on the publisher's release channel and same-channel checksums. The fixed launch allocation directs two 5% subsidy shares to hardcoded addresses, whose keyholders we have not established. These are concentration and software-supply trust points, not proof of an active selective-sell rugpull.”
