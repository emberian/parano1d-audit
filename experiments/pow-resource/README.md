# Block producer resource pricing audit

Target: `parano1d` at `52938433a30b185ab007afaa15166a632cf2e82e`. This is a source audit and cost model. I did not run another devnet or claim that the modeled maximum block has been accepted by recursive proof verification. Another lane was using the shared host for a multi-node run.

## Finding: a producer recovers ordinary creation fees, but must pay for fresh slots

`CreateCollection` is live (`noid_tx/src/native_assets/transition.rs:44,269-285`). One creation consumes a unique ordinary funding input, derives the collection ID from that exact input (`transition.rs:309-327`, `native_assets.rs:277-313`), and creates one native collection output. The existing creation-spam lane established a valid 1-input/1-output creation with `fee = 5,800 μNOID`, `burned = 0`, and a zero-valued native output. It also measured about 441 B of logical node-local carriage for a collection versus 102 B for a plain UTXO, and about 192 B per collection on a cold snapshot transfer (`experiments/creation-spam/README.md`).

Consensus prices only `max(0, outputs − inputs)` as state-growth burn (`noid_chain/src/consensus/fees.rs:94-120`). It adds all fees **minus that burn** to the producer's permitted coinbase (`consensus/validation.rs:248-287`, `consensus/emission.rs:109-144`), and the node-owned template does the same (`consensus/template.rs:935-952`). A producer who owns the funding input recovers the full 5,800 μNOID fee by mining its own collection transaction. The fee is a liquidity and fee-market cost for a non-producer, but it is not a permanent token cost for a self-producer. The collection consumes its funding UTXO permanently; it cannot reuse one input incarnation for many distinct collections. The one-input version needs an input amount of 5,800 μNOID; with multiple inputs, the designated funding input merely needs to be nonzero and the input sum must cover the fee (`native_assets.rs:283-294`, `transition.rs:183-208`).

To continue beyond a pre-existing UTXO inventory, the producer must split value into fresh ordinary inputs. A 1-input/128-output ordinary PagedSpend can produce 127 exact-5,800 μNOID funding UTXOs plus a change output in 64 pages (`noid_tx/src/paged_spend.rs:42-54,415-483`). At low occupancy, its exact required fee is `5,000 + 100 + 128×700 + 127×2,500 = 412,200 μNOID`; **317,500 μNOID is burned**. The producer may reclaim the remaining 94,700 μNOID through its coinbase. It needs at least 1,148,800 μNOID plus the change value in the splitting input for that example (127×5,800 of funding, plus the full fee); the 127×5,800 comes back as claimable fees after those collections are mined. The funding outputs must precede their collection spends in different blocks: cross-transaction input/output slot reuse in one block is rejected (`consensus/checks.rs:48-63`).

Each native collection group has at least two fixed pages, a header and a data page (`noid_tx/src/native_assets/wire.rs:383-421,820-825`). There are at most 255 effective non-primary-coinbase page positions per block, including a scheduled development payout (`consensus/params.rs:139-161`, `consensus/template.rs:309-340`). Thus **127 collections per block** is a page-budget ceiling for an already-funded burst; it is not a demonstrated full-block construction. At 30-second target intervals, an attacker producing *every* block could, in that burst ceiling, turn 365,760 existing UTXOs/day into collections. That corresponds to about 161 MB/day of collection records, **124 MB/day more** than leaving those UTXOs plain, and about 70 MB/day of added future cold-sync payload, using the earlier lane's per-object layouts. These are logical row counts, not MDBX file-growth measurements.

Sustaining that burst with new funding inputs also consumes block pages. A preparation group creating 127 funding outputs needs 64 pages, so the amortized page budget for **split-funded** collections is `2 + 64/127 ≈ 2.504` pages per collection, or about **102 collections/block** before discrete packing and scheduled development payouts. A miner can also use at most one new primary coinbase output per block as a direct funding input, with a change output and a 2,500 μNOID net-slot burn; this can add roughly one collection/block to the split-funded rate. At the illustrative 102/block split-funded rate, the low-occupancy state-growth burn is about **734 NOID/day** for new input inventory, and the collection records occupy about **130 MB/day** across each full node (**100 MB/day more** than plain UTXOs), plus **56 MB/day** for every later cold sync. Occupancy pressure can multiply the 2,500 μNOID burn by 2, 4, or 8 (`consensus/fees.rs:24-88`); state expansion can lower the multiplier again. The attacker also needs enough valid PoW to win the fraction of network blocks it fills. None of these figures equates a local genesis-floor PoW rate with current mainnet mining cost.

This corrects the gross-fee framing of item spam too: a self-producing miner can recover the claimable portion of item-mint fees, but not the **2,500 μNOID per net-new item** low-occupancy burn. The earlier lane's 496-item/block burst has a 3,571.2 NOID/day minimum burn at 2,880 blocks/day, versus its quoted 4,609 NOID/day gross fees (`experiments/creation-spam/README.md`). Fee recapture changes the attacker's token outlay; it does not erase PoW opportunity cost or state-growth burn.

**Assessment:** low-to-medium, economic availability pressure rather than free or unbounded amplification. Creation converts a plain slot into larger permanent native records without an incremental burn, while a sustained campaign still pays to make new slots and consumes finite block capacity. The development allocation does not divert ordinary fees: only the miner's subsidy is shared (`consensus/development_allocation.rs:1-11`).

## Reorg resident-segment cap: future-profile candidate, not a present finding

The MDBX reorg preflight unions all segments touched by replacement block inputs/outputs and the reverted branch's undo logs. It rejects a union above 512 segments (`noid_chain/src/storage/mdbx_context.rs:318-348,1995-2035`), whereas a single block may touch 256 (`consensus/params.rs:166-171`, `consensus/validation.rs:163-210`). This initially looked like a higher-work fork could be rejected after a shallow, dispersed old branch. The capacity bound changes that conclusion for today's genesis-capacity profile: `log_slots = 24` and `segment_size = 2^16` give **only 256 possible segment IDs** (`consensus/params.rs:295-303`). The first expansion gives 512, still at the reorg cap. A union above 512 requires `log_slots ≥ 26`. Reaching that requires the second expansion, which in turn requires at least 10 of 18 finalized headers at **25,165,824 active slots** or more (75% of `2^25`; `consensus/slot_expansion.rs:18-61`).

I have not built competing valid branches at `log_slots = 26`, measured the resource error with a real reorg, or established whether the node then performs a successful snapshot rebase. The node classifies `ResourceLimit` as a local rather than body-peer fault (`noid_node/src/main.rs:4272-4292`), and exact-suffix failure logs without committing the candidate (`main.rs:13495-13534`), but that is insufficient to assert a persistent fork-choice failure. Treat this as a future-capacity test target; do not cite it as a current exploit.

## Other bounds checked

- A block has at most 256 fixed bodies, 255 effective user-page positions, 1,020 live user inputs, 510 live user outputs, 1,531 actions, and 256 touched segments (`consensus/params.rs:139-171`). The decoder's canonical block cap is 82,905 B plus separately bounded native openings, and the HistoryStep terminal is capped at 1.1 MB after v1.1 (`consensus/wire_limits.rs:27-79,171`). These caps prevent an unbounded single-block byte or segment bomb, though they do not price permanent historical state.
- V2 ASERT uses the **parent** timestamp for a child's target, so siblings cannot choose easier target from their own timestamps (`consensus/difficulty.rs:65-75,128-155`). Headers still require exact expected target, median-time-past and a 120-second local future-drift bound (`consensus/header.rs:209-244`, `consensus/timestamps.rs:17-56`). I did not establish an own-PoW timestamp discount or a cheap proof-verification asymmetry.

## Evidence limits

The collection creation and carriage figures were demonstrated by the existing isolated PoC; this lane independently checked fee recapture, page/slot budgets, and the reorg capacity correction in source. The 127 collection burst, split transaction, and steady-state rate are bounds and arithmetic examples, **not** new accepted-block or recursive-proof PoCs. The actual current network difficulty, miner share, storage file allocation, and long-run proof cost are not inferred from these local bounds.
