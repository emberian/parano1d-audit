# Software distribution and bootstrap controls

Target: `parano1d/` at `52938433a30b185ab007afaa15166a632cf2e82e` (the release-relevant files checked against `v2.1.0` in [REPORT.md](REPORT.md)). This source review did not connect to mainnet. Domain administration, development-fund key ownership, mining work, and release-account ownership require separate evidence.

## Summary

The reviewed reference node has **no identified remotely activatable administrative key, privileged transaction, update feed, mutable consensus checkpoint, or address-specific transfer restriction**. Its genesis, fork schedule, network profile, proof banks, and development payout recipients are compiled or embedded. A newly installed release can contain changed behavior; the already installed binary does not acquire new rules merely because a new release appears.

The clearest network-facing administration point is four default, identity-unpinned DNS seeds under `parano1d.org`. Whoever controls their DNS answers can choose a fresh node's initial endpoints. When no independent peers are reachable, this can impair discovery or bias the initial view. DNS answers do not authorize invalid state or erase a returning node's finalized chain. This review does not establish who administers the zone. See [the separate bootstrap survey](../operator-power/REPORT.md) for dated DNS observations and [snapshot review](../snapshot-adversary/REPORT.md) for the work-ranked initial-sync boundary.

## Distribution and new installations

The documented release procedure starts from synchronized, clean `main`, runs Platform CI, creates an annotated tag on canonical Forgejo plus GitHub and GitLab mirrors, opens a GitHub draft, and dispatches Native Release (`scripts/publish_release.sh:175-223,288-316`; `.github/RELEASING.md:1-17`). Native Release is manually dispatched and requires the tag, pack SHA-256 values, and successful Platform CI for that exact commit (`.github/workflows/release.yml:5-39,165-171`). It verifies pack archive digests and layouts before the five platform builds, then uses those approved archives (`release.yml:173-205,299-337`). Current default is `retired_history=true`; legacy matrices are omitted, with the embedded verified ancestry certificate supplying the transition (`release.yml:35-39,323-337`; `.github/RELEASING.md:35-43`). The legacy-matrix gap in standalone `build_release.sh` therefore does not directly affect default v2.1 artifacts; [C16 reassessment](REPORT.md) gives the narrower transition/custom-build boundary.

The workflow publishes `SHA256SUMS` alongside the ten binaries and three packs (`release.yml:418-456`). Users are told to compare downloads to that same-release file (`docs/getting-started/wallet.md:20-37`). The comparison detects byte differences against the listed hashes. When an artifact and its checksum are both obtained from the same release channel, the comparison does not independently authenticate that channel's contents. The scripts show reproducible **pack normalization** and checked build inputs; this review found no independent, publicly verified bit-for-bit rebuild of the published v2.1 executables. The release scripts do not create a detached artifact signature. The macOS packaging default uses ad-hoc `codesign --sign -`, with an optional identity; the user guide says Windows Authenticode signing and Apple Developer ID notarization are not in place (`scripts/release/package_macos_gui.sh:117-128`; `docs/getting-started/wallet.md:56-67`). An annotated Git tag identifies the release source in these scripts but does not independently authenticate binary contents.

A **modified, newly installed** node or GUI could reject selected transactions locally, change wallet-send destinations, disclose local secrets, change bootstrap names, or apply different consensus rules. That is the software-distribution trust boundary: the user must run the changed executable or point the GUI at a different RPC endpoint. Existing nodes would continue applying their own consensus rules. A policy to omit otherwise valid transactions would require adoption by miners or relays with enough reach to sustain censorship; this review did not measure that reach. The inspected v2.1 code does not exhibit those modified behaviors.

## Concise summary

“In the reviewed reference client, no remote mechanism was identified for address-specific transfer restrictions or privileged spending. A clean installation bootstraps from four unpinned DNS names under one domain. Official binaries are distributed through a release channel with same-channel checksums. The launch allocation directs two 5% subsidy shares to fixed addresses; this review did not identify their keyholders.”
