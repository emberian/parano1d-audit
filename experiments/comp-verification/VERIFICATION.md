### Consensus and proving

- **High-bit slot index:** Production `noid_recursive/src/acceptance/block_slots.rs` binds Merkle path bits without an apparent constraint that `slot_index < 2^log_slots`. A range-check helper in `trace/exact_state.rs` has no production caller. This is a plausible assembled-circuit gap. Ordinary witness construction rejects out-of-range slots; no complete malicious HistoryStep proof, accepted terminal, or snapshot split has been produced. The next discriminating check is the full assembled relation and verifier at the pinned schedule.
- The new `comp-consensus-diff/REPORT.md` calls this a concrete snapshot split and says its PoC proves acceptance. Its own later section says no second test run was started after source edits; the saved log still has 50 compile errors. Even if its gadget checks later pass, the current test does not call `MdbxChainContext::verify_snapshot_boundary` or produce a serialized full HistoryStep proof. Severity and end-to-end reachability remain open.
- **Financial opcode partition:** `noid_tx/src/native_assets/profile.rs` enables eleven opcodes that the v2.1 sequential Native class excludes. `experiments/verification-opcodes/` repaired Gemini's uncompiled fixture and generated a real V4 owner proof for an op49 LaunchRequest paired with its mandatory op50 RegisterLaunches. The pair passed standalone native block checks and financial state materialization on a synthetic parent. The normal template, candidate-history, sequential-header R1CS gate, and mempool admission rejected op49. This is an API/profile partition, not an accepted active-schedule block or chain halt. The other ten codes were not individually executed. The same lane authenticated the pinned v2.1 bank digest and capacities.
- **Definition capacity:** V2.1 config sets capacity to `headers + markets`; the definition table asserts that witness length fits, while candidate preflight lacks an explicit definition-count check. Gemini's proposed test used invalid ghost authorizations and did not reach a real candidate. `experiments/verification-definition-capacity/` generated real V4 owner proofs and used a supported 63-page research class with definition cap five: two launches (four definitions) passed binder and candidate, while three launches (six definitions) passed native validation and candidate preflight but the same binder panicked. Normal mempool selection chose only two. The pinned mainnet bank independently decodes to capacity nine; five immediately graduating launches appear to exceed it with ten definitions while fitting other relevant resources, but that is source extrapolation. The parent state is synthetic and no mainnet-class full HistoryStep prover or accepted block was run.
- **C0 BaseFold T2 root:** A component check finds unchanged Fiat-Shamir challenges when the root changes at `log_batch_size = 0`. It produces no verifier-accepted forged proof. Production HistoryStep uses C1, which absorbs T2 before round zero.
- **Merkle direction and PoW nonce:** `experiments/verification-circuit/` built a full standalone FieldR1cs proof with a MerkleRegionSidecar callback: the verifier accepted direction `D=2` with altered public entry digest and unchanged root. It rejected the original-entry public IO and a production-style Boolean-pin control rejected the altered witness. Production HistoryStep allocators pin that direction bit. The same lane's inline PoW R1CS accepted a nonce with `hi=1` through the 16-bit filter, while an explicit 64-bit pin rejected it. Neither is a full HistoryStep forgery, native-serialized nonce, or reduced-work result.

### Miner and wallet behavior

**No chainwide halt was demonstrated.** Two source paths may cause a *local miner* to return no template under particular conditions; neither invalidates honest blocks or shows that every miner stops.

- **Reorg across slot-domain expansion:** A newly posted storage report identifies a credible conditional node failure. Reorg rollback calls `shrink_to_log_slots`, which flushes raw dirty segments and asserts on an evicted segment; compact startup marks persisted live segments both evicted and dirty, while undo preloading hydrates only touched segments. The original synthetic test neither compiled nor ran a reorg. Our isolated `experiments/verification-reorg/` release test *did* reproduce the assertion in the same shrink primitive under evicted metadata, while a resident control shrank and preserved its root. Mainnet `log_slots` 24→25 expansion first requires at least 12,582,912 active slots through the finalized window, then a competing valid fork; no full MDBX reorg was run. The report's lock-poisoning and process-termination claims are incorrect: the node uses Tokio `RwLock` and maps a panicked blocking worker to an error. A panic could leave partly reverted RAM state before recovery; that remains to be demonstrated.

- **Stale exact financial fee:** Mempool rechecks fees below a new minimum; financial application requires exact equality; template-building maps an application error to `None`. Gemini's proposed fixture fabricated a 50% occupancy transition and did not compile. `experiments/verification-stale-fee/` compiled and ran a corrected conditional fixture: a signed CreateLaunch entered under a synthetic high-pressure resident view at 13,100 μNOID, an authentic accepted block moved to an exact 10,600-μNOID fee, and the stale intent remained selected while the production chain template returned `FinancialBlockError::Fee`. Empty and fresh 10,600-μNOID templates succeeded. The threshold-crossing admission state was still synthetic, the accepted block used a stubbed HistoryStep terminal verifier, and the full `noid_miner::TemplateBuilder`/release daemon was not driven to failure.
- **Coinbase hydration:** A metadata-only snapshot can leave segments evicted when a shortcut sees holes in a loaded segment; the pure builder cannot use reserved holes or unloaded populated segments. Our bounded `experiments/verification-template/` test ran against pinned production `noid_chain`: with two parent holes reserved by a selected spend and another populated segment evicted, the pure builder returned `NoCoinbaseSlot`; with that segment loaded and the same root, the control built a template. This reproduces the allocator/hydration predicate, not a real persisted mainnet chain, `TemplateBuilder` result, or daemon halt. A miner selecting no conflicting transaction may hydrate another usable segment.
- **Financial fee floor:** `experiments/verification-fee-floor/` reproduced the conflict with real signed transactions and production `AsyncMempool` admission. Twenty-three native-consensus blocks reached the isolated v2.1 activation; four signed ordinary spends raised a capacity-five pool's local floor to 90,000 μNOID while one slot remained free. The same signed CreateLaunch was accepted by a fresh pool and rejected by the pressured pool at its exact 8,600 μNOID fee. The chain fixture stubbed HistoryStep terminal verification, and the pool size/window were scaled down. This proves local admission incompatibility, not consensus exclusion or network-wide market freeze.
- **Trade-intent floor latch and funding budget:** `experiments/verification-trade-latch/` admitted three genuinely V4-proved, funded policies for an unindexed asset, then two signed high-fee ordinary spends in a capacity-six local pool. After a PoW/MDBX block, the three policies remained at half capacity and the 90,000-μNOID floor persisted; the same exact-fee CreateLaunch passed a fresh pool and failed the latched pool. The terminal verifier callback was stubbed and the pool scaled down from production 1,024. The claimed 794-entry case requires distinct live funding outputs, valid V4 proofs, and sustained admission at scale, none of which were measured. Gemini's original scaled runner bypassed authorization verification and did not advance an accepted block. A synthetic 64-input trade reaches resource accounting, but no admitted-and-assembled trade or block demonstrated the claimed cross-market displacement.
- **Trade selection source review:** `experiments/verification-trade-scholar/` confirms the shared 64-funding-input budget and a conditional path where recomputing a batch can replace earlier selected trades. A 64-input trade still needs genuine funding/proof, a fill, first selection, and a winning Native class. Amount only selects the priority anchor; the score is parent-bound and hashes the anchor creation ID/slot. Gemini's 47-sell displacement ignores that each sell needs at least token and NOID fee inputs, leaving at most 31 sells plus a one-input buy under the shared limit. No valid admitted-and-mined example or repeatable trader delay was shown.
- **Pre-graduation redemption:** `experiments/verification-redeem/` executed the pinned transaction transition for a valid 100,000-token launch. Redeeming 10,000 creator-bought tokens burned those owned units, paid 10,000,000 μNOID from separate backing, and left a pre-fee 28,888,889-μNOID loss for that trader; foreign-owner and LaunchState-as-balance controls rejected. Graduation quantities conserved in the component quote. This is self-funded holder action, not a confiscation or network availability issue. Gemini's proposed 1,000-token launch violates the pinned minimum and did not establish a boundary failure.
- **Wallet reservations:** Reorg ordering can install wallet reservations from a pre-reorg mempool snapshot and update the mempool later. Dismissing activity does not separately clear `native_pending`. `experiments/verification-wallet/` first reproduced the generic eviction lock with a controlled `ChainView` and then with two PoW-valid local MDBX blocks. The strongest release-mode run generated genuine HistoryStep terminals and independently accepted both bundles on a second local MDBX chain through `apply_next_block` and `runtime.verify_terminal`. After block 2's coinbase occupied the pending wallet send's chosen output slot, `AsyncMempool` evicted the real wallet-proved transaction while the wallet input stayed reserved, spendable balance remained zero, and address discovery failed. Restart cleared the in-memory lock but retained an unconfirmed history row. `experiments/verification-operator-wallet/` found that the stock miner normally avoids known pending output slots; the fixture instead chose the wallet output hint to match the predicted coinbase. Consensus seems to permit a custom producer to place coinbase into another empty slot, but no targeted producer was tested. This is an ordinary-payment local wallet effect, not demonstrated token-sale suppression or arbitrary-victim control. The proposed one-missed-block CreateListing eviction is contradicted by the current listing definition and expiry checks.
- **RPC fee figure:** `experiments/verification-rpc-fee/` built a signed three-page CreateLaunch on an isolated v2.1 chain. The exact RPC per-page expression reported 10,600 μNOID, while the production template's coinbase was only 8,100 μNOID above schedule-aware subsidy; the 2,500 difference was the logical group's state-growth burn. A one-page ordinary spend matched at 100,000 in both. The native block passed production checks/materialization, but the HTTP RPC handler and HistoryStep verifier were not run. This is a miner-facing reporting discrepancy, not a consensus burn bypass.
- **Shorter-heavier reorg receipts and wallet discovery:** `experiments/verification-receipts/` committed a shorter-heavier PoW/MDBX reorg and used an actual Merkle receipt. Normal wallet reorg installation removed the old receipt. A cut after chain commit and before wallet cleanup left the orphan visible through wallet receipt listing; a subsequent replacement-height block did not immediately remove it, but the next startup reconciliation did. The fixture stubbed HistoryStep proof verification and did not run daemon/P2P. The `walletDiscoverAddresses` RPC drops its chain read lock before `commit_address_discovery`; a reorg may acquire its chain write lock and reach wallet installation while that commit proceeds without the wallet operation gate. The interleaving is source-reachable but has not yet been driven through a full RPC/MDBX reorg.
- **Reorg wallet ordering and local artifacts:** `experiments/verification-wallet-race/` admitted a valid wallet-proved transaction, captured reservations, used a controlled replacement owner snapshot, and observed actual mempool `OutputSlotOccupied` eviction after the wallet installed pre-reorg reservations. A post-eviction reservation control restored spendability. A separate deterministic two-thread wallet-function interleaving changed `next_index` during installation, causing orphan receipt/history cleanup to be skipped; a no-discovery control pruned them. The RPC drops the chain read lock before its wallet commit, so the schedule has a source-level opening, but no concurrent full MDBX/HistoryStep reorg RPC was run. Full daemon startup reconciliation would remove a canonicality-contradicted orphan receipt; the direct wallet reload in the fixture does not run it. The same lane showed an object opening file persisted before admission, a local artifact side effect.
- **Local owner-index damage:** `experiments/verification-storage-indexes/` deleted one owner-index row directly from local MDBX after a valid h1. Restart and an h2 commit did not rebuild it. The clean twin accepted the same h3 two-input spend that the corrupted twin rejected twice with `missing pre-block owner-index record`; the corrupted twin accepted a coinbase-only h3. A malformed one-byte row failed closed on lookup. The setup uses direct local database writes and a stubbed HistoryStep terminal verifier; no remote ingress or network-wide halt follows from this result.

### Cryptography and snapshot boundaries

- `noid_soundness` uses `.max()` where a heterogeneous-class worst-case calculation needs `.min()`. The stated `49/36` undercharge uses a constructed mixed `m=24,25` profile; both classes in the currently loaded certificate use 12 squeeze permutations. A numerical undercount in that certificate was not shown. The certificate tool is separate from consensus verification.
- Poseidon2b parameter subfield closure and the `CryptographicHasher` implementation ignoring its receiver IV are supported by source and local checks. `experiments/verification-crypto/` found a *fully padded generic zero-IV sponge collision* for two distinct chosen 64-byte messages after 73,494 restricted first-block trials, and the trait's concatenation method returned the same digest. Tagged byte-hash and exact-state node-hash controls differed. The pinned tree has no non-test direct `poseidon2b_digest`/`hash_concatenation` caller; FRI Merkle inner nodes use the tagged `compress` override, and the wallet keystore's zero-IV 64-byte input fixes the second block while its first block is a 256-bit master secret. No valid Merkle-leaf collision, forged proof, consensus-root conflict, or wallet compromise was shown. A uniform 256-bit wallet master secret enters the searched restricted first-block set with probability `2^-224`.
- The non-x86/aarch64 `Flat<Block128>` basis inconsistency is source-supported but untested on those targets. The `noid_fri` transcript/root concerns are library-level, with no production wallet or IVC call path shown.
- The `noid_pruv` SMT claims concern a developer tool, not a consensus verifier. Its README limits `pruv verify` to per-call integer-program postconditions and says spending policy needs separate analysis. A `Verified` result for an uncallable policy, or a counterexample when an unconstrained fee exceeds a bound, is compatible with that contract. Gemini's overflow example violates the tool's documented defined-arithmetic precondition and has no run result.
- `experiments/verification-object-planner/` reproduced the static zero-address difference: an object opening with zero authorities/recipients validates and roundtrips, while `pruv native` rejects a zero `Owner`. Creating that opening returns a descriptor; funding it is a separate wallet action. Static native templates accept distant positive expiry and large token amounts, but the planner checks current-height expiry and available balance. These are voluntary configuration and preview boundaries, not an operator freeze or extra-token path. The same lane traced CD-4: the standalone consensus helper has no pinned Rust caller, and live accepted-bundle materialization follows terminal binding/verification.
- The snapshot-terminal harness intends to use a genuine terminal and release joiners, but had no result at review. It runs at heights 1–54, before V2/V2.1 activation; its separate V2.1 calculation uses fabricated headers rather than a V2.1 proof.
- The ASERT/MTP run uses synthetic ancestor headers, omits PoW for its first required hard block, and compares declared work to a zero base. `experiments/verification-asert/` independently reproduced the arithmetic and found all five shifted headers too far in the future at the saved fixture clock; they become timestamp-admissible only after about 4,375 seconds from the anchor. Twenty-three floor blocks add 6,029,312 work, whereas the unmined first hard block supplies 4,825,867,084,694 of the report's work. One extra equal-hard honest block takes 18,409,222 floor blocks to catch up. The extreme-target clamp case requires an unmined first block with expected 2^256 trials. This is no valid alternate fork or chain takeover.

The next high-value checks are a full-R1CS verifier check for the high-bit relation and bounded, compiling miner-template tests on valid chain states. Those are research priorities, not established chain or snapshot failures.
