# P2P capacity envelope under bounded multi-source load

Target: `parano1d` at `52938433a30b185ab007afaa15166a632cf2e82e`. Assessment dated 2026-11-15. This is a source review of the pinned implementation and a synthesis of previously saved, isolated local experiments. No public peer was contacted and no new load test was run for this report. “Twelve computers” has no intrinsic protocol meaning: identities, public address groups, upload bandwidth, and the receiving node's resources are the relevant quantities. GPU count matters only when the sender supplies valid proof of work, which this P2P study does not model.

## Short answer

The strongest *measured* anonymous availability effect is C17: one peer's stalled mempool responses held a node's entire 64 MiB outbound response reservation domain, and a fresh joiner's state installation was delayed. The joiner still selected the honest headers, eventually installed state, and the multiple-peer run recorded no `Busy` response. C18 showed a separate header memory and preparation cost, but its large-response test used consensus-invalid database rows and all honest reads completed. C22 showed that anonymous direct transaction Push reaches the expensive verifier, but its bounded real-node run admitted the honest control. A larger, geographically distributed sender could place more independent identities within the configured limits; the observed runs do not establish a sustained outage, transaction censorship, or a way to make an invalid chain win.

These are upper bounds on *admission at individual stages*, not a promise that traffic reaches every stage. For example, the per-peer transaction count says nothing about an external sender's sustainable upload rate or the target's Noise/yamux throughput. A connection count does not establish control of the victim's locally selected outbound peers.

The mempool response reservation is unusually sensitive to a modest number of sources because it reserves **16 MiB per response even when fewer bytes are served**. More than two identities were unnecessary to fill that one domain in the multi-peer fixture; additional hosts matter for reaching *more targets* or for spreading identities across address limits, not for increasing its 64 MiB cap. In contrast, the header preparation and proof-verification concerns scale with offered work from independent identities, subject to the receiving node's bounded queues and the sender's bandwidth.

## Twelve-host/IP-pool envelope

For a public target, the configured transaction Push allowance is `5 × admitted PeerIds` per second, capped by connection and address admission. Using **only** the saved 90.4 KB proof fixture and its **single-machine** 415.5/s drain gives these arithmetic points:

| Admitted identities | Configured Push allowance | Fixture bytes if every allowance is used | Comparison with fixture drain |
| ---: | ---: | ---: | --- |
| 32 (one public IP's peer bound) | 160/s | ~14.5 MB/s | Below 415.5/s |
| 96 (one coarse group's connection bound) | 480/s | ~43.4 MB/s | Above 415.5/s, **modeled only** |
| 128 (swarm inbound ceiling, requiring multiple groups) | 640/s | ~57.9 MB/s | Above 415.5/s, **modeled only** |

At approximately 84 admitted identities, the arithmetic allowance crosses 420/s, corresponding to about 38 MB/s for this fixture. These are decimal MB/s and ignore transport overhead. A dozen computers could in principle host this many identities, but computer count by itself neither supplies enough distinct public IPs nor guarantees those upload rates, durable connections, a full verifier queue, or exclusion of honest peers. The target's CPU, ingress link, relay path, connection churn, and queue/drop behavior were not measured at this scale. The direct-Push route is the relevant modeled proof-ingress path; the 64 MiB/10 s gossip byte window would allow only about 74 of these 90.4 KB payloads per second averaged over its window, before accounting for block announcements and other gossip.

For **honest service**, the bounded multi-source picture is mixed:

* An inbound-heavy source set can occupy public inbound slots and increase contention for the same node's response and proof budgets. It cannot, merely by occupying inbound slots, replace the node's locally selected outbound neighbours or exceed the process-global byte reservation cap. The explicit per-IP and per-group reserves make a single public origin weaker than a distributed one.
* When C17 pins a *particular provider*, its budget-participating body, terminal, and State serving may wait. A joining client with another honest provider can still progress, as in phase 7. Its separate header path continued selecting honest work. It is unknown whether enough public providers share the mempool precondition and could be simultaneously constrained.
* Header service has a distinct weakness: the preparation cap protects CPU concurrency, but not post-preparation stalled-write memory. Its observed latency effect required the artificial large-row fixture. Real-chain compression, active peer mix, and memory headroom determine whether this matters in deployment.
* At sufficiently high proof ingress, 1,024 delivery records and the bounded event lane can preserve memory yet drop a later honest transaction locally. This is a **source-derived conditional** outcome, not observed in the 40-push control. Other honest peers and later relay/retry may still deliver it. The same four verifier permits serve legitimate transactions, so queue delay is a plausible user-facing effect before any network-wide loss.

Proof of work can buy a different kind of node attention. A [separate source review](../new-avenues/REPORT.md) traces a valid, higher-work header with advertised but unavailable exact objects into the non-isolated miner's unresolved-better-header readiness gate. That path would spend real PoW and has no measured pause duration or demonstrated live-node effect; stronger honest work or real object availability may end it. It is a candidate to price against honest mining work, not a consequence of adding IPs or of the anonymous C17/C18/C22 capacities above.

The P2P measurements do not support selective selling or operator-only censorship. Those require a different analysis of transaction validity, wallet dependencies, block production, and network topology. P2P resource pressure can delay a node's view or service, but the saved runs did not show that it selectively suppresses one holder's transaction while preserving another's.

There is no justified network-wide numerical ceiling in these data. The table bounds **one receiving node**. Multiplying it by an assumed public-node count would silently assume identical mempools, reachable addresses, available upload, and enough simultaneous attacker connections to each node. The saved joiner used other honest providers successfully. A global service claim needs a measured provider graph and client failover behavior, neither of which is supplied by a dozen-host count.

## Engineering priorities and measurement gaps

1. **Charge mempool responses for actual encoded bytes.** Preserve the process-global bound, but avoid a 16 MiB reservation for every response. A dedicated mempool sub-budget would also prevent this service from consuming all object and State response capacity. Regression checks should include a full legal mempool, a near-empty mempool, and an honest joiner during a stalled reader.
2. **Bound header write lifetime by memory, not just preparation workers.** Carry a byte or response-count permit through the codec's final write, with a reserve for honest header fetches. Measure on consensus-valid long histories before assigning a deployment severity.
3. **Make proof admission fair across sources.** Track verifier queue wait, in-flight proof count, byte permits, drops, and honest-admission latency by source group. A bounded invalid-proof cache or shared per-group work allowance could reduce repeat work, but should preserve legitimate retries when chain state changes. Prioritize honest chain processing separately from anonymous proof verification.
4. **Measure failure domains, not only identity counts.** In an isolated, permissioned setup, compare one and multiple address groups, locally selected outbound service, honest wallet delivery, and a cold joiner. Record delivered verifier executions and actual wire bytes; sent frames and configured maxima alone are insufficient. Revisit the untested established-honest-mesh topology in the Sybil report before treating first-hop dilution as an availability finding.

No hardware hash-rate or Internet bandwidth assumption is embedded in these estimates. The values above come from pinned code and saved local runs; deployed-node capacity and twelve-host feasibility remain unmeasured.
