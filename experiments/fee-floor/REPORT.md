# Fee-floor manipulation and selective-exit hypothesis

Source audit of pinned `parano1d/` commit `52938433a30b185ab007afaa15166a632cf2e82e`, 2026-11-15. No live-network traffic, exchange interaction, local miner, or transaction-proof generation was used. This is a bounded code-path analysis, not a demonstrated devnet exploit.

## Result

**Mining high-fee self-transfers does not, by itself, raise anyone's fee floor.** The floor is local node state, derived from the last 50 **admitted mempool** fees, not from block fees. Under the v1.1 policy it is exposed only after either mempool count or retained bytes reaches 80% of its limit. A block that confirms the high-fee transactions removes them from the pool, and the floor resets if the remaining pool falls below both 50% limits (or empties). Fresh nodes start at the base floor.

**A narrower local manipulation is plausible:** fill a node's pool with valid, low-fee transactions first, then admit high-fee transactions last. At the default 1,024-transaction cap, 770 low-fee transactions followed by 50 at 100,000 μNOID reach 820 entries, pass the 80% threshold, and put 50 high fees in the median window. The relay floor becomes 90,000 μNOID. Confirming just the 50 high-fee transactions leaves 770 low-fee transactions pending. The floor's historical median is not recomputed from remaining entries, and 770 is above the 50% reset boundary, so the floor can remain 90,000 despite no high-fee transaction remaining. This is conditional on all 820 transactions passing admission, having distinct usable inputs/slots and valid authorizations, reaching the target node, and staying pending in sufficient number. It has **not** been driven through a running node here.

This local gate is not a consensus freeze or a developer-only right. A new transaction paying the raised floor is still admitted. A valid transaction paying only the deterministic consensus fee may be included directly by a willing producer, even when the producer's or another node's mempool would reject it. A producer that can consistently omit others' transactions can cause selective inclusion without manipulating the fee floor; this audit does not establish that the developer has that production power.

## Cost and persistence model

For a 1-input/1-output ordinary self-transfer at low state occupancy, the consensus minimum is `5,000 + 100 + 700 = 5,800 μNOID`, with zero net-new-slot burn (`fees.rs:99-160`; constants in `params.rs:428-446`). A fully funded 820-entry count-pressure example with 770 such low-fee entries and 50 entries at 100,000 μNOID has **9.466 NOID of stated fees at risk**: 4.466 NOID in low-fee entries plus 5 NOID in high-fee entries. These are not prepaid on mempool admission. If a miner other than the attacker confirms them, it may claim those non-burned fees; if the attacker confirms them in its own blocks, it may reclaim them through coinbase. Self-reclamation requires winning the relevant PoW block race; the fee is a transfer to whichever producer wins, not a costless refund the spammer can demand. The attacker also needs 820 distinct live inputs, enough value to fund fees and nonzero outputs, proof-generation/relay capacity, and possibly earlier state-growth fees to create that inventory. This arithmetic is an illustration, not a measured attack cost or a claim that an operator currently owns that inventory.

The historical-median latch makes the example last beyond confirmation of the 50 high-fee transactions **if** the low-fee backlog remains above the reset boundary. Ordinary miners choose high fees first, then can drain the low-fee backlog; with enough included entries, the floor resets. To keep the floor raised across that drain, the attacker must continuously replenish with transactions paying the current raised floor, control which valid entries are mined, or keep the targeted node separated from producers that drain the pool. A producer can omit the backlog in its own blocks, but then the selective effect follows producer discretion, not a protocol-mandated fee rule. At the next transaction-epoch anchor change, stale anchored entries are evicted (`noid_mempool/src/pool.rs:771-779`); this epoch is **144 blocks** (`noid_chain/src/consensus/params.rs:226`, `epoch_anchor.rs:62-70`), distinct from the six-block PoW difficulty epoch.

Relayed admissions are gossiped (`noid_node/src/main.rs:2354-2373`), so a valid flood can reach multiple nodes, but each node maintains its own floor. Admission order, differing pool contents, and block-drain timing can diverge. A new node that has not admitted the flood begins at 5,000 μNOID (`pool.rs:2043-2051`). A user's own node may reject an ordinary-fee deposit while another accepts or a producer directly includes it. We did not test whether a specific exchange accepts deposits through any particular node or whether the alleged operator can isolate a holder's only submission path.

## Evidentiary conclusion

The most defensible claim is **temporary, node-local fee inflation and admission disruption by valid transaction congestion**, with a sticky high median above the low-water mark. The capital and authorizations are real prerequisites, but a miner who wins its own fee-bearing transactions can recover most of the fee value. The code does not support the stronger claim that self-funded on-chain block fees alone create a network-wide floor, nor that this mechanism gives the developer an exclusive ability to sell. A devnet test with 820 real valid intents and independent producers would determine how long the raised floor persists under actual proof throughput, gossip, template capacity, and block arrival; this source audit does not claim that result.
